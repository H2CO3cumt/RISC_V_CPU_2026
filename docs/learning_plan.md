# 工程掌握学习计划（任务驱动）

> 最后更新：2026-09-17
> 用途：用任务驱动的方式把本仓库工程掌握到"能答辩、能被追问"的程度。按任务推进，不按天推进——前期任务小、反馈快，后期任务大、需要沉淀。
> 进度记录：完成的勾选 `[x]`，并在每个阶段末尾的复盘小节写下日期与遗留问题。

## 0. 使用说明

### 0.1 学习方法（重要）

本项目按 `AGENTS.local.md` §2.1 的规则推进：**RTL 由学习者本人编写，Agent 只做审查、独立 Testbench、Regression 和 Debug 支持**。因此本计划的定位是：

- 不是"把别人的东西背下来"，而是成为这套工程的真正掌握者；
- 目标不是"读过代码"，而是能回答三类追问：**为什么这么设计**、**数字从哪来**、**边界在哪**；
- 评委不会问你写了什么，只问"为什么"和"数字"。计划里的每个任务都围绕这两件事设计。

### 0.2 使用规则

1. **不要跳任务。** 验收不通过就重做当前任务，不进入下一个阶段。
2. **T07、T16、T23、T24 是四个"必须能讲出来"的任务**，其余是"必须能答出来"。答辩现场扣分基本出在这四个上。
3. **前期快、后期慢是正常的。** 后期变慢通常说明前面的支点没打牢，应回头补而不是硬推。
4. **不要碰本届范围外的东西。** Cache、异常/中断、RLE 按 `AGENTS.md` 均为冻结项，学了用不上且浪费时间。
5. **每个任务过关后更新** `docs/progress.md` 或本文件的进度记录小节。

### 0.3 阶段总览

| 阶段 | 名称 | 任务 | 特征 |
|---|---|---|---|
| 0 | 摸底 | T01～T07 | 7 个快任务，30～60 分钟/个，有即时反馈 |
| 1 | 数据通路与冒险 | T08～T11 | 需要逐周期推演 |
| 2 | 控制冒险与性能 | T12～T16 | 答辩主线素材全部在这里 |
| 3 | Core/SoC 解耦与接口 | T17～T19 | 理解解耦边界 |
| 4 | 应用闭环 | T20～T22 | 软硬件协同 |
| 5 | 答辩准备 | T23～T25 | 时间最长、最不能省 |

## 阶段 0：摸底（7 个快任务）

### - [ ] T01 摸清仓库地图

- **读**：`docs/progress.md` 前 60 行；根目录与 `rtl/`、`tb/`、`scripts/`、`fpga/`、`software/`、`python/` 一级目录
- **产出**：一张纸写下 `rtl/` 中属于 **CPU Core** 的文件与属于 **SoC 外设** 的文件，各列一类
- **验收**：能指着目录说出 Core 与 SoC 的分界线在哪，并说出这条边界是谁规定的

### - [ ] T02 只看接口，不看实现

- **读**：`rtl/*.v` 所有 `module` 的**端口列表**（只抄端口，不读 `always` 块）
- **产出**：一张端口总表
- **验收**：看到 `i_req_*` / `i_rsp_*`、`d_req_*` / `d_rsp_*`、`trace_*`、`event_*` 四组信号，能说出各自属于哪个边界、服务什么用途

### - [ ] T03 RV32I 指令格式

- **读**：`docs/rv32i_instruction_coverage.md`
- **自检**：B 型和 J 型的立即数为什么要错位重排？最低位为什么不存？
- **验收**：随手给一条 `beq` 机器码，能拆出 opcode / funct3 / rs1 / rs2 / imm

### - [ ] T04 单周期 CPU 怎么跑一条指令

- **读**：`rtl/single_cycle_cpu.v`、`rtl/imm_gen.v`、`rtl/decoder.v`
- **产出**：画出 `lw x5, 0(x1)` 的信号流（PC → IMEM → Decoder → RegFile → ALU → DMEM → WB）
- **验收**：能说出这条指令在哪些信号上产生了副作用

### - [ ] T05 五级流水骨架

- **读**：`rtl/pipeline_cpu.v` 第 111～143 行
- **产出**：纸面画出 IF/ID/EX/MEM/WB，标出四个流水寄存器各存什么
- **验收**：能回答"为什么 WB 只有一拍"和"`memwb_valid<=0` 为什么放在块首"

### - [ ] T06 单个模块的读法

- **读**：`rtl/branch_unit.v`（全文，组合逻辑，量小适合起步）
- **验收**：能解释为什么异号时 signed 比较只看符号位，以及非法 `funct3` 时输出什么

### - [ ] T07 逐周期推演（硬门）

- **做**：选 `ADDI → ADD → SW` 三连，**不看代码**，逐拍写出 PC、RegFile、DMEM 的值
- **验收**：与仿真日志对得上；错一处就重推，直到一次通过
- **⚠️** 这是整套学习法的质量门，`docs/progress.md` 对本项目明确要求过。**这一关过不了，后面全是空中楼阁。**

## 阶段 2：控制冒险与性能（答辩主线素材）

### - [ ] T12 分支/跳转到底怎么处理

- **读**：`rtl/pipeline_cpu.v` 第 58～65 行、第 127 行
- **自检**：`ex_redirect` 为什么用"或"把 `idex_jump` 无条件并进去？被冲刷的指令去哪了？
- **验收**：能解释错误路径的 Store 为什么不会产生副作用

### - [ ] T13 BTB 结构

- **读**：`rtl/branch_predictor.v`（62 行，逐行推）
- **自检**：`counter[x][1]` 为什么就能表示"跳"？新建项为什么初始化成 `2'b10` 而不是 `2'b11`？
- **验收**：手推连续 3 次 taken 后计数器如何变化，以及第 4 次查询会预测什么

### - [ ] T14 预测怎么影响取指（本项目最难的一段）

- **读**：`rtl/pipeline_cpu.v` 第 80～84 行、第 130～141 行（`if_arm` 段）
- **自检**：什么叫"单 outstanding"？`if_req` 与 `if_arm` 为什么要两个信号表达同一件事？
- **验收**：能画出"请求被接受当拍武装下一笔请求"的时序图，并说明它省掉了哪一拍

### - [ ] T15 性能计数器

- **读**：`rtl/perf_monitor.v`、`rtl/perf_mmio.v`
- **验收**：能说出各计数器分别统计什么，以及 `clear` 为什么要单列一个写入口

### - [ ] T16 归因主线（**必须能用自己话讲出来**）

- **读**：`docs/coremark_cpi_analysis.md`、`docs/rtl_changes.md` §改动 2
- **验收**：能讲出下面这条完整因果链，且被追问三层不倒——

> 原设计取指事务在"请求被接受的下一拍"没有请求在场 → 取指只能每两拍一条 → 用与实体板逐拍同源的观测台定位到这一点（口径自证差 0.1%）→ 在请求接受当拍立即武装下一笔请求 → 恢复每拍一条 → CPI 2.3443 → 1.5388，Score 29.559 → 45.051 → 50/80 MHz 双频交叉验证（CPI 差 0.006%）

## 阶段 5：答辩准备（时间最长，最不能省）

### - [ ] T23 数字溯源到文件（**必须能讲出来**）

- **做**：把技术报告、PPT、视频脚本、答辩稿里出现的**每一个数字**，追到具体证据文件
- **产出**：一张"数字 → 证据文件 → 运行口径"对照表（表头见附录 B，可逐条填入）
- **验收**：随机抽 10 个数字，都能说出"在哪个文件、哪次运行、什么口径"
- **⚠️ 必然遇到的一致性问题**：85 MHz 是**时序证据**，实体板实跑是 **80 MHz PLL**，两者绝不能混写成"85 MHz 上板成绩"

### - [ ] T24 异常现象反推（**必须能讲出来**）

- **做**：挑一个真实 bug，从现象一路追到根因。推荐二选一：
  - `docs/debug_log.md` 中"Capture Engine 在分频采样下每系统时钟更新 `previous_sample` 导致边沿丢失"
  - 实体板 static 回环"期望 A5、实际 AF"（旧 J8 约束导致通道输入悬空）
- **验收**：能讲成一个三分钟完整故事，包含**第一个错误信号**和**第一个错误周期**，并说明修正后加了哪条定向测试
- **为什么做这个**：每一个 bug 都是能讲三分钟的深度故事，比背架构图管用得多

### - [ ] T25 全盘拷问

- **做**：让人连问 20 个"为什么"（同学、老师，或让 Agent 扮演评委），答不上来的记下来回去补
- **验收**：随机抽 10 个模块，**不看代码**说出其输入输出、关键信号、最易出错的地方
