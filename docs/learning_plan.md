# 工程掌握学习计划（重建优先）

> 最后更新：2026-09-17
> 用途：用任务驱动的方式把本仓库工程掌握到**能重建**的程度，而不只是"能解释"。
> 进度记录：完成的勾选 `[x]`，并在每段末尾的复盘小节写下日期与遗留问题。

## 0. 使用说明

### 0.1 这份计划的定位

本计划的目标是**吃透工程**，不是准备答辩话术。两者的方法完全不同：

- **准备答辩**：读代码 → 能解释 → 组织叙事。**读就够。**
- **吃透工程**：读图纸 → 重建 → 多视角反复 → 自己推出演进链。**只有重建才够。**

因此本计划把"重建"放在正中间（第二段），把"讲"降到可选加餐（附录 C）。若时间紧张，**优先保第二段**。

### 0.2 三种"懂"，以及本计划的验收线

| 层级 | 表现 | 何时达到 | 有用吗 |
|---|---|---|---|
| A. **认得出** | 打开文件能跟上，觉得"哦原来是这么写的" | 约 1 周 | **没有用，而且危险** |
| B. **能解释** | 不看代码能说出模块干什么、为什么这么设计 | 约 2 周 | 有用，但会被追问击穿 |
| C. **能重建** | 能从零推出来，能说出"改这个信号，第几拍会错" | 约 3～4 周 | **本计划的验收线** |

A 层是最危险的：`rtl/pipeline_cpu.v` 只有 126 行，读五遍之后每条线都眼熟，那种"我懂了"的感觉非常强，但它是假的。**破解办法只有一个：关掉文件写出来。**

### 0.3 工程量实测（为什么一个月足够）

| 范围 | 行数 |
|---|---:|
| **真正要吃的 Core（11 个文件）** | **993 行** |
| SoC + 外设（12 个文件） | 1,091 行 |
| 全部 RTL | 2,137 行 |
| 全部文档（22 篇） | 2,859 行 |

**核心只有约 1000 行 Verilog。** 按每天认真啃 40 行算，25 天啃完——瓶颈从来不是阅读量，而是"读了不等于懂了"。

### 0.4 四条硬规则

1. **优先级顺序**：图纸（第一段）→ 重建（第二段）→ 多视角（第三段）→ 演进链（第四段）。**不要跳到多视角阶段去"深挖"，没有图纸和重建打底，深挖是空转。**
2. **重建任务的唯一做法**：先关掉所有文件凭理解写，写完再开原文对比。**先看原文再写等于没做。**
3. **多视角是本计划的灵魂**：同一个硬点要在不同日子用不同视角反复看 3～5 遍。这不是低效，这是唯一有效的深层理解方式。
4. **知道哪些不用懂**：见附录 A。厂商 IP、工具链、管脚约束、标准 UART 都不需要吃透，别在那里耗时间。

### 0.5 四段总览

| 段 | 名称 | 任务 | 建议占比 | 产出 |

| 一 | 图纸 | T01～T05 | 25% | 手绘数据通路图 + 端口总表 |

## 第四段：整体演进（从"懂每一块"到"懂整个设计怎么长出来的"）

### - [ ] T17 演进链自述（**吃透的最终验收**）

- **做**：合上所有文件，用一张纸写出这个设计的**演进过程**，每一步都要回答"为什么必须加"：

  1. 单周期 CPU：能跑 RV32I，但没有吞吐量
  2. 五级流水：吞吐上去了 → **新问题**：RAW 冒险
  3. Forwarding：解决大部分 RAW → **新问题**：Load 结果来不及
  4. Load-Use 暂停：解决 Load 依赖 → **新问题**：分支要等判定
  5. 分支/Jump 冲刷：解决控制冒险 → **新问题**：冲刷代价高
  6. BTB + 2-bit 计数器：减少冲刷 → **新问题**：预测正确也被无条件重定向
  7. 取指满速交接（`if_arm`）：消除取指空洞 → CPI 降到 1.5388

- **验收**：能画出这条链并说清每一步的"新问题"是什么。**如果某一步的"新问题"说不出来，说明那一步你没真懂，回第二/三段补**
- **为什么这是最终验收**：会解释现有代码，和能推出这个设计怎么长出来的，是完全不同的两种能力

## 附录 A：不需要吃透的清单（知道哪些不用懂，和知道哪些必须懂一样重要）

| 内容 | 为什么不用吃透 | 你只需要会什么 |
|---|---|---|
| `pll_80m.v` 里的 `GTP_PLL_E3` | 厂商 IP，内部不可见也不需要 | 说清分频参数怎么算（`IDIV=1, FDIV=16, ODIV0=10 → 80 MHz`），以及为什么 PGL50H 无法精确产生 85 MHz |
| DebugCore / Fabric Debugger | PDS 工具链，非本设计代码 | 说清探针宽度/采样深度、怎么用 TCL 模式抓波形 |
| `.fdc` 约束、管脚电平 | 查手册的活，不是设计原理 | 说清 P20/R8/R9、按键低有效/LED 高有效的来源 |
| J8 隔行相邻脚对（`3/4、7/8…`） | **物理接线约束**，不是设计选择 | 说出为什么不能用连续脚（会与地/电源脚冲突） |
| `rtl/decoder.v`(258 行) | 基本是一张 case 表，无算法难点 | 说出它输出哪些控制信号、非法指令怎么处理 |
| `rtl/uart_tx.v`/`uart_rx.v`/`uart_mmio.v`(429 行) | 标准 8N1 UART | 说清波特率分频怎么算（80 MHz 下分频 694）、RX 的三个 sticky 状态位 |
| `rtl/soc_fpga_memory.v`(130 行) | 存储器行为模型 | 说清它是**仿真/板级存储器模型**，不参与 Core 设计 |

> 原则：**厂商 IP、工具链、约束、标准外设 → 会查会说即可。真正的设计智慧全在 Core 的 993 行里。**
