## ① 这个模块在数据通路里是什么位置

**先用大白话说它是干什么的。**

一个 CPU 出了事（算错了、读到不该读的地方、外面有设备喊它），它得先**把这件事记在一本台账上**，
然后才能跳去处理。这本台账要记三样东西：

1. 出事的是哪条指令（回来要从哪儿接着干）；
2. 出的是什么事（哪一类错，或者哪个设备喊的）；
3. 出事的细节（错的地址、错的指令码）。

这本台账，在代码里就叫 **CSR（Control and Status Register，控制状态寄存器）**，
而 `rtl/csr_unit.v` 就是**专门管这本台账的那一个模块**。

> **这个比方在哪儿不准**：台账是死的，只记不管；但这个模块还管一件活的事——
> 出事的那一拍它要**顺手把"允许打扰"的开关关上**（代码里叫 `mstatus.MIE`），
> 免得刚跳进处理程序、还没站稳，同一个设备又喊一次。
> 所以它是"记账 + 关一个开关"，不是纯记账。

**再给真名。**

| 大白话 | 代码里的名字 |
|---|---|
| 台账 | `csr_unit.v` 里的那 12 个 `*_q` 寄存器 |
| "回来从哪继续" | `mepc`（Machine Exception Program Counter） |
| "出的是什么事" | `mcause`（Machine Cause） |
| "出事的细节" | `mtval`（Machine Trap Value） |
| "允许打扰"的开关 | `mstatus.MIE`（Machine Interrupt Enable） |
| "上次的开关状态" | `mstatus.MPIE`（Machine Previous Interrupt Enable） |
| "处理程序从哪开始" | `mtvec`（Machine Trap Vector） |

**谁跟它说话**（这是理解它的关键）：

- 它是**叶子模块**：不例化任何别的模块，只跟时钟、复位和顶层 `pipeline_cpu.v` 打交道。
- 顶层**从不自己改**这些状态，只往这里送**两个单周期的脉冲**：
  - `trap_enter`（该进 Trap 了，第 39 行）
  - `trap_return`（该从 Trap 回来了，也就是 `MRET`，第 43 行）
- 所以顶层那 1089 行里所有"要不要 Trap"的判决，最后都收敛成**这两根线上的一个高电平**。
- **按 `docs/learning_plan.md` §0.2 纪律 1（自顶向下），这个模块排在顶层 `pipeline_cpu.v` 之后读**：
  先在顶层看清"是谁、在什么条件下按下这两个按钮"，再进来看账本怎么记。
  读子模块之前先读父模块，是为了避免把 `csr_illegal` 这样的输出误解成一个孤立的判定——
  它在顶层要跟 `csr_we` 的门控配合才成立（见 §④ 第 2 条）。

## ③ 逐段讲解（按行号区间）

### 段 1：文件头注释（第 1～18 行）—— 先读这里，能省很多事

第 3～5 行立了一条规矩：**契约里没列出的 CSR，读和写都报非法，绝不静默读 0、绝不静默忽略写。**
第 7～10 行解释了为什么单独做成一个模块：① 它是**纯架构状态**，复位后必须回到确定初值，可以独立 Testbench；
② 流水线里所有"要不要 Trap"都只是组合查询，真正动状态只在两个脉冲上。

第 12～18 行是全文件最容易搞错的一点，专门写了口径：
**进 Trap 时 `epc_next` 送进来的是"下一条将要执行的指令地址"，不是"出错指令的 PC"。**
为什么这样反而两种情形都对：

- 同步异常：出错指令被取消、没退休，所以"下一条"恰好就是**它自己的 PC**；
- 中断：中断点之前那条指令正常退休，"下一条"就是**还没执行的那条**，`MRET` 之后从那里继续，不会重复执行。

> 这一段说白了就是：**谁来记、记什么、以及"回来从哪继续"这个值由谁算。**

### 段 2：端口（第 19～60 行）

见 §② 的表。这一段只做一件事：把"读口 / 写口 / 合法性检查口 / Trap 两口 / 中断展示口 / 退休口"分清。
重点注意 **合法性检查口与写口是分开的**（第 28 行 vs 第 33～36 行）：
本模块**不自己拦**非法写，它只**报告**"这次不合法"（`csr_illegal`），由顶层决定怎么办。

### 段 3：CSR 编号与架构状态（第 62～93 行）

第 65～77 行：13 个 CSR 编号写死成 `localparam`，包括 `mcycle/mcycleh/minstret/minstreth` 这四个计数器
（它们不是普通状态，见段 5）。

第 82～93 行：真正的状态只有 **12 个寄存器**（`mcycle` 与 `minstret` 各是 64 位，占两个 32 位读口）。

### 段 4：读通路与位段（第 95～136 行）—— 组合逻辑，最容易读错的地方

这是本模块第一个"必须逐位看懂"的地方。`mstatus` 一共 32 位，本项目**只实现 3 个位**：

- `MIE` 在 bit 3（总开关）
- `MPIE` 在 bit 7（上一次的开关状态）
- `MPP` 在 bit 12～11（恒 `00`，因为只有机器模式）

所以第 97～98 行是**手写对齐**的拼接：

```verilog
wire [31:0] mstatus_rdata = {19'b0, 2'b00, 4'b0, mstatus_mpie_q,
                             3'b0, mstatus_mie_q, 3'b0};
```

数一下位宽：19 + 2 + 4 + 1 + 3 + 1 + 3 = **33 位**，比 32 位多了 1 位。
但赋值给 `[31:0]` 时被截掉的是**最高位**，而最高位恰好属于最前面那段填充用的 `19'b0`，
所以截断之后 `MPIE` 仍然在 bit 7、`MIE` 仍然在 bit 3、`MPP` 仍然在 bit 12:11——
**和注释里写的位段意图完全一致**。

> **结论：这是"填充位数多写了一个 0"的写法问题（顺带注释里 `4(10:7)` 是个笔误，
> 按意图应当是 `3(10:8)`），不是功能缺陷。**
> 证据不是推理，而是项目自己已经 PASS 的测试：`tb/tb_csr_unit.v`
> 第 145 行断言 `mstatus = 32'h0000_0088`（= bit7 + bit3），
> 第 210 行断言 Trap 后 `32'h0000_0080`（= 只剩 bit7），
> 第 219 行断言 `MRET` 后回到 `32'h0000_0088`，全套 **32/32 PASS**。
> 也就是说"`MPIE` 在 bit 7"是**实测过**的。

第 102～103 行是同一种写法，给 `mie` 只实现 `MSIE[3] / MTIE[7] / MEIE[11]`。
第 107～108 行是 `mip`：它**不是寄存器**，是一个只读窗口，直接把三根外部中断输入摆到对应位上。
第 111 行是 `misa`，写死 `32'h4000_0100`（MXL=32 位 + 只有 I 扩展），只读。
第 114 行是 `mtvec`：**只支持 Direct 模式**，`mode[1:0]` 读出来永远是 `00`。

第 119～136 行是读的组合 `case`：13 个地址各返回什么，其余一律 `32'b0`。第 134 行的 `default` 只是"读个 0"，
**不合法的判定不在这里**（见段 6），这是初学者最容易混的一处。

### 段 5：`mcycle` / `minstret`（第 198～202 行）

第 198 行：`mcycle_q <= mcycle_q + 64'd1;` —— 每个时钟沿都加 1，不看别的条件。
第 200～202 行：`minstret_q` 只在 `retire` 为 1 时加 1。顶层的 `retire` 接的是 `wb_fire`，
也就是"真正形成提交记录的那一拍"（`pipeline_cpu.v` 第 561～563 行）——
**被 Trap 取消的出错指令、气泡、以及没退休的指令都不计数**。

### 段 6：合法性判定（第 138～162 行）

两个条件，任一成立就算非法：

1. `addr_implemented`（第 146～158 行）：地址不在那 13 个里面 → 未实现；
2. `addr_read_only && csr_check_write`（第 139～144 行）：`misa/mip/cycle/cycleh/instret/instreth` 是只读的，
   却要写它 → 非法。

第 160～162 行把它们合起来，并且**前面加了一个 `csr_check_en` 门控**：
非 CSR 指令（`csr_check_en = 0`）永远不会被判成"CSR 非法"。

### 段 7：写掩码（第 164～180 行）

第 175～179 行按同样的位段把 `csr_wdata` 里**实现位**抽出来。
第 180 行：写 `mtvec` 时 `{csr_wdata[31:2], 2'b00}`，把 mode 强行清成 Direct。

### 段 8：唯一的时序块与优先级（第 182～237 行）—— 全文件的重点

第 183～196 行是 `reset` 分支：**12 个状态全部回确定初值**，中断使能是**关**的（第 184～188 行）。
注意第 189 行 `mtvec_q <= 32'b0`：复位后 Trap 入口是 0 地址，所以软件**必须**先写 `mtvec` 才能用 Trap。

接下来是一条 `if / else if` 链，**优先级从高到低**（第 204～215 行）：

| 顺序 | 条件 | 做什么 |
|---|---|---|
| 1 | `trap_return`（`MRET`） | `MIE ← MPIE`，`MPIE ← 1`（第 205～206 行） |
| 2 | `trap_enter` | `MIE ← 0`，`MPIE ← 旧 MIE`，`mepc/mcause/mtval` 写入（第 208～214 行） |
| 3 | `csr_we` | 按 `csr_waddr` 分派，按掩码改对应状态（第 215～235 行） |

为什么第 1 条排在 `trap_enter` 前面**不会出错**：顶层已经保证两者互斥——
`pipeline_cpu.v` 第 530 行写着 `wb_trap_return = memwb_valid && memwb_trap_mret && !trap_take`，
Trap 同拍时 `MRET` 直接被取消。

为什么进 Trap 要 `MIE ← 0`：不关的话，Trap 入口那条指令还没执行，同一个中断（电平还在）会立刻再打断一次。
为什么 `MPIE ← 旧 MIE`：`MRET` 时要**恢复成进入 Trap 之前的开关状态**，而不是无脑打开。

第 228 行：写 `mepc` 时 `{csr_wdata[31:1], 1'b0}` —— bit0 清 0（指令地址恒为偶地址）。
第 231～233 行的 `default` 只写了一句注释：非法或未实现的写在 `csr_illegal` 那一步已经被顶层拦住了，
这里不再动作。**这就是"两处配合"的地方，见 §④。**

### 段 9：输出（第 239～244 行）

把内部状态引到端口上，唯一值得注意的是第 243 行 `mtvec_base = mtvec_rdata`：
出去的是**清过 mode 的版本**，不是原始的 `mtvec_q`。

## ④ 设计取舍与陷阱

| # | 容易误以为 | 实际是 |
|---|---|---|
| 1 | `csr_rdata` 是个寄存器 | 它是**组合**的（第 119～136 行），当拍就能用。正因如此 EX 级才敢在同一拍完成 CSR 读改写 |
| 2 | 非法判定与拦截都在 `csr_unit` 里完成 | 只做**判定**（第 160～162 行）。拦截发生在顶层：`csr_we` 被 `&& !csr_illegal_q` 门控（`pipeline_cpu.v` 第 546 行）。**两处缺一不可** |
| 3 | 写 `mip` 能改变中断挂起 | `mip` 是**只读窗口**（第 107～108 行），直接反映外部电平，不锁存、不清除。这是"中断源属于 SoC"这条边界在 RTL 上的落点 |
| 4 | `mtval` 是本模块算出来的 | 不是。它在顶层按异常种类算好（`pipeline_cpu.v` 第 520～527 行），本模块只负责存 |
| 5 | `epc_next` 就是"出错指令的 PC" | 文件头第 12～18 行专门澄清：它是**下一条将要执行的指令地址**，两种情形（同步异常 / 中断）才都自动正确 |
| 6 | 复位后 `mtvec` 有个合理默认值 | 复位值是 **0**（第 189 行），软件不先写 `mtvec` 就用 Trap，会跳到 0 地址 |
| 7 | `mcycle` 与 `minstret` 是一回事 | 不是。`mcycle` 每拍都加（第 198 行）；`minstret` 只在 `retire` 时加（第 200～202 行），被 Trap 取消的指令不计 |

## 参考答案（答完再看）

**第 1 题**：拼接一共 **33 位**（19+2+4+1+3+1+3），比 32 位多 1 位。
赋值给 `wire [31:0]` 时，Verilog 的规则是**从最高位截断**，被丢掉的是最前面那段 `19'b0` 里的一个 0，
所以下面所有位的**位置都不变**：`MPP` 在 bit 12:11、`MPIE` 在 bit 7、`MIE` 在 bit 3。
因此 `mstatus_mpie_q` 落在 **bit 7**，写法虽然冗余（填充多写了一个 0、注释里 `4(10:7)` 也是笔误），
但**功能是对的**。这不是我的推理结论，而是 `tb/tb_csr_unit.v` 第 145/210/219 行用
`0x88`（bit7+bit3）与 `0x80`（bit7）断言过、并已 32/32 PASS 的事实。
👉 **要建立的判断习惯**：看到"位宽对不上"先别急着报 bug，要先算清**截断发生在哪一端**。

**第 2 题**：因为中断源、使能、优先级、聚合全部属于 **SoC**（`AGENTS.md` §8）。`mip` 若可写，
Core 内部就出现了"谁能产生中断"的状态，等于把设备语义塞回 Core。做成只读窗口后，
Core 只知道"外面有人在喊"，不知道喊的是谁。

**第 3 题**：并列 `if` 会让同拍多个动作**同时发生**（Verilog 非阻塞赋值是"最后写的赢"，
但这里的三个分支写的是**同一个** `mstatus_mie_q`）。具体场景：`trap_enter` 与 `csr_we` 同拍
（顶层正是靠优先级把这种 CSR 写取消掉的），并列写法会让 `csr_wdata` 的值覆盖 Trap 的结果，
`mstatus.MIE` 可能被"写回 1"，于是 Trap 入口立刻又被同一个中断打断——形成中断风暴。

**第 4 题**：架构上，非法 CSR 指令会**留下副作用**（真的改了 CSR），违反契约 §3.3 第 3 条
"非法指令不得产生任何架构副作用"。实测现象：`tb/tb_trap_pipeline.v` 的
"写只读 CSR 报非法且不动状态"一类的断言会失败；`mcause` 会记成非法指令，但被写的那本台账已经变了值。
（`tb/tb_csr_unit.v` 里也有一条对应的独立断言。）

**第 5 题**：这一拍 **`trap_enter` 赢**。
- `csr_we`：被顶层门控成 **0**（`&& !trap_take`，第 546 行），所以这次 CSR 写**不生效**；
- `trap_enter`：**1**；
- `csr_wdata`：照旧由组合逻辑算出（值是多少都无所谓，因为 `csr_we` 已经是 0）；
