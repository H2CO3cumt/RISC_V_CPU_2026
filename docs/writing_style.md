# 设计文档与中文技术写作规范

> 适用范围：本项目所有面向交付的中文技术文档（竞赛设计文档、接口文档、进度、报告等）。
> 核心依据：阮一峰《中文技术文档的写作规范》（[github.com/ruanyf/document-style-guide](https://github.com/ruanyf/document-style-guide)），并按本项目的竞赛设计文档需求做了适配。
> 原则：可读性优先、风格全篇统一、数字与事实可追溯、引用必注出处。
> 交稿自检：所有交付文本在提交前必须逐条过 §9「去 AI 腔清单」。

---

## 1. 标题

- 层级分为四级：
  - 一级标题：文档标题
  - 二级标题：主要部分的大标题
  - 三级标题：二级下面的小标题
  - 四级标题：三级下面某一方面的标题
- 一级标题下不能直接出现三级标题（不许跳级）。
- 避免孤立编号：同级标题只有一个时应合并或删减。
- 下级标题不重复上一级标题的名字（如"概述"下不要再叫"概述"）。
- 谨慎使用四级标题：三级标题下有并列内容时，优先用项目列表，而不是拆四级标题。

## 2. 文本

### 2.1 字间距

- 全角中文字符与半角英文之间，应有一个半角空格。
  - 错误：本文介绍如何快速启动 Windows 系统。
  - 正确：本文介绍如何快速启动 Windows 系统。
- 全角中文与半角数字之间，有没有空格均可，但**必须全篇统一**，不能两种风格混杂。
- 半角百分号视同阿拉伯数字：经济增长率是 6.5%。
- 英文单位若不翻译，数字与单位之间留空隙：一部容量为 16 GB 的智能手机；1 h = 60 min。
- 半角英文/数字与全角标点之间不留空格：他的电脑是 MacBook Air。

### 2.2 句子

- 避免长句：单句尽量不超过 20 字；20～29 字可接受；30～39 字语义必须明确；**40 字以上任何情况不接受**。
- 以逗号分隔的长句，总长度不超过 100 字或正文 3 行。
- 尽量用简单句和并列句，避免复合句。
  - 并列句：他昨天生病了，没有参加会议。
  - 复合句：那个昨天生病的人没有参加会议。（不推荐）
- 同样意思优先用肯定句，不用否定句。
  - 错误：请确认没有接通装置的电源。
  - 正确：请确认装置的电源已关闭。
- 避免双重否定：正确写法是"用户必须拥有删除权限，才能删除此文件"。

### 2.3 写作风格

- 优先主动语态，少用被动语态。
  - 错误：假如此软件尚未被安装。
  - 正确：假如尚未安装这个软件。
- 不用非正式语言、网络口语（如"酷毙了""给力"），用书面语。
- 不用冷僻、生造或文言词语，用现代汉语常用表达：
  - 错误：这是唯二的快速启动的方法。
  - 正确：这是仅有的两种快速启动的方法。
- 用对"的、地、得"：开心的笑容（形＋的＋名）；开心地笑了（副＋地＋动）；笑得很开心（动＋得＋副）。
- 使用代词（其、该、此、这）时必须明确指代，保证只有一个含义。
- 名词前不要堆砌过多形容词；把过长的修饰语拆成短句。

### 2.4 英文处理

- 英文原文复数译成中文时还原为单数：RAMs → 随机存取存储器（RAM）。
- 外文缩写可用半角圆点：U.S.A.、Apple, Inc.。
- 表示中文时，英文省略号 `...` 改为中文省略号 `⋯⋯`。
- 英文书名/电影名译成中文时，双引号改书名号：他发表了一篇名为《航空业的未来》的文章。
- 英文词汇第一次出现时，括号内给出中文标注；此后直接用缩写即可：
  - IOC（International Olympic Committee，国际奥林匹克委员会），此后直接用 "IOC"。
- 专有名词每个词首字母大写，非专有名词不大写。
  - 专有：American Association of Physicists in Medicine（美国医学物理学家协会）
  - 非专有：online transaction processing（在线事务处理）

## 3. 段落与引用

- 一个段落只能有一个主题（一个中心句子）。
- 中心句放在段首，概述全段；后面的句子为它服务。
- 段落长度不超过七行，最佳小于等于四行。
- 用陈述、肯定语气，避免感叹语气。
- 段落之间用一个空行隔开；段落开头不留空白字符。
- 引用第三方内容必须注明出处；全篇转载在开头显著位置注明作者、出处并链接原文；外部图片在下方或文末标明来源。

## 4. 数值

- 阿拉伯数字一律半角：价格是 1000 元（不是 １０００ 元）。
- 千位以上加千分号（半角逗号）：实收资本为 ￥1,258,000；4 位数值（1000）千分号可选。
- 货币用阿拉伯数字，数字前写货币符号或数字后写中文名称：$1,000 / 1,000 美元。
- 数值范围用波浪线（～）或一字线（—）连接；**带单位或百分号时两个数字都加单位/百分号**：132 kg～234 kg；67%～89%。
- 区分"了"（增量）与"到"（定量）：
  - 增加到过去的两倍（过去 1，现在 2）；增加了两倍（过去 1，现在 3）。
  - 降低到百分之八十（原来 100，现在 80）；降低了百分之八十（原来 100，现在 20）。
- 禁止"降低 N 倍/减少 N 倍"的说法，改用"降低/减少百分之几"。

## 5. 标点符号

- 中文语句一律用全角标点，与全角文字视觉一致；整句为英文时用半角标点。
- 句号、问号、叹号、逗号、顿号、分号、冒号**不得出现在一行之首**。
- 点号（句号、逗号、顿号、分号、冒号）不得出现在标题末尾；标号（引号、括号、破折号、省略号、书名号、叹号、问号）可以。
- 句号：中文结尾用全角 `。`；句末括号加注时句号在括号之外。
  - 正确：请参照第 1.3 节（见第 26 页）。
- 逗号：避免"一逗到底"——整个段落除结尾外全部用逗号。
- 顿号：中文句子内部并列词用顿号 `、`，即使并列词是英语：
  - 正确：我最欣赏的科技公司有 Google、Facebook、腾讯、阿里和百度等。
- 分号 `；`：复句内部并列分句之间的停顿。
- 引号：全角双引号 `“ ”`，前后不同；引号内再引时外层双引号、内层单引号 `‘ ’`。
- 括号：补充说明用全角圆括号 `（）`，括号前后不加空格。
- 冒号：需要解释的词语后用全角 `：` 引出说明；表示时间用半角 `:`（早上 8:00）。
- 省略号：`⋯⋯` 占两个汉字空间、六个省略点，不用 `。` 或 `...`；**不与"等"同用**（"香蕉、苹果、梨等各色水果"与"有香蕉、苹果、梨⋯⋯"二选一）。
- 感叹号：平静叙述，尽量避免；不得连用（`！！`、`!!!`）。
- 破折号：`————` 占两个汉字位置，用于进一步解释；若只占一字则前后留半角空格。
- 连接号：
  - 复合词、图表编号用半角直线 `-`：氧化-还原反应；图 1-1。
  - 数值范围（日期、时间、数字）用波浪线 `～` 或一字线 `—`（全角）：2009 年～2011 年；前后两个值都建议加单位。
  - 波浪连接号可用汉字"至"代替：-20 °C 至 -10 °C。

## 6. 文档体系与文件命名

- 手册类文档建议结构：简介（必备）→ 快速上手 → 入门篇（必备）→ 环境准备（必备）→ 安装 → 设置（必备）→ 进阶篇 → API → FAQ → 附录 → Glossary → Recipes → Troubleshooting → ChangeLog → Feedback。
- 文件名不得含空格；必须用半角字符，中文不能用于文件名。
- 文件名建议全小写；`README`、`LICENSE` 等说明文件可大写。
- 多单词文件名用半角连词线 `-` 分隔：`advanced-usage.md`。
- **本项目取舍**：`docs/` 现有文档全部采用小写下划线命名（如 `fpga_platform.md`），为保持一致，本项目沿用下划线；此点有意偏离阮一峰建议，以全仓风格统一为准。

## 7. 本项目设计文档结构（竞赛模板）

按竞赛设计文档模板逐节编写，以下结构与字数限制为硬约束：

- **作品名称**：不出现涉及学校名称等内容。
- **摘要**：800 字内。
- **第一部分 作品概述**
  - 1.1 功能与特性：400 字内（可加重要图）
  - 1.2 应用领域：400 字内（可加重要图）
  - 1.3 主要技术特点：400 字内
  - 1.4 主要性能指标：200 字内（建议用表格）
  - 1.5 主要创新点：200 字以内（逐点给出）
  - 1.6 设计流程：200 字内（可加重要图）
- **第二部分 系统组成及功能说明**（图文结合，阐述设计细节）
  - 2.1 整体介绍：系统整体框图，各子模块标注清楚，文字说明模块间关系
  - 2.2 硬件系统介绍：2.2.1 硬件整体介绍；2.2.2 机械设计介绍（从总体到局部，可 CAD 截图或手绘）；2.2.3 电路各模块介绍（从总体到局部，标出关键输入/输出信号线，可电路图/SCH/PCB 截图）
  - 2.3 软件系统介绍：2.3.1 软件整体介绍（含 PC 端或云端，结合关键图片）；2.3.2 软件各模块介绍（按总体框图，从顶层到底层给出各函数流程图及关键输入、输出变量）
- **第三部分 完成情况及性能参数**（图文结合，实物照片为主）
  - 3.1 整体介绍：系统实物正面、斜 45° 全局照片
  - 3.2 工程成果：3.2.1 机械成果；3.2.2 电路成果；3.2.3 软件成果（界面照片）
  - 3.3 特性成果：逐个展示功能、性能参数等量化指标（可加仪器测试或现场照片）
- **第四部分 总结**
  - 4.1 可扩展之处：300 字内
  - 4.2 心得体会：1000 字内，可包括研发和制作细节
- **第五部分 参考文献**：标准格式，限 20 篇以内

## 8. 配图约束（去除 AI 作图痕迹）

设计文档中的插图（架构图、框图、流程图、示意图等）一律遵守：

- 图面只保留与主题直接相关的模块、标注、信号与数据；**不得出现"注：""说明：""来源：""备注："等注释性小字**。
- 图中**不得出现内部文档路径、文件名（如 docs/interfaces.md）、工具名、项目内部流程名（如 Roadmap、Testbench、Gate）等评审无关信息**。
- 图例、图注或必要说明（如"图 2-1 系统整体框图"）一律放在正文中，不画进图内。
- 图面风格简洁专业：统一字体与配色、模块框对齐、连线含义明确；不得出现水印、来源标识、装饰性元素或任何形式的生成痕迹。
- 所有指标、数值与术语与正文一致，可追溯但不在图中标注来源。
- 重新生成或修改图时同样遵守本条，生成后需检查图面是否残留此类小字。

## 9. 去 AI 腔清单（交稿自检）

清单主体整理自两个 MIT 许可的开源写作 Skill：[leter/zh-tech-writing](https://github.com/leter/zh-tech-writing) 的「AI 腔清单」与 [luoling8192/technical-writing](https://github.com/luoling8192/technical-writing) 的证据先行写法，示例改写成本项目的 RISC-V 语境。

本节与本文件其他条款冲突时，按以下顺序：§7 的模板与字数 → §5 的标点符号（省略号 `⋯⋯`、双引号 `“ ”`、破折号 `————`）→ 本节。外来的省略号和引号写法不覆盖本文件既有约定。

### 9.1 用事实代替形容词

写性能、写实现、写难点，一律落到可核对的数字、信号名、文件、命令或波形上。

- 差：流水线性能得到了大幅提升。
- 差：BTB 显著降低了分支惩罚。
- 好：加入 16 项 BTB 后，CoreMark cycles 从 1,604,264 降到 1,251,724，分支冲刷从 161,742 次降到 69,120 次。
- 好：S3 的 I-Cache 把 cycles 从 1,251,724 抬到 2,891,324，按止损条件默认关闭。

三条硬要求：

1. 材料里的每个数字都要能在 `release/evidence/claims_map.md` 找到同值和出处的证据文件。查不到的数字不写。
2. 实测值、PDS 估算值、RTL 仿真值必须分别标明来源，不得混写。例如 89.2538 MHz 是 PDS 估算，板上最高实测是 85 MHz。
3. 不确定就写清条件。“可能”“也许”“大约”要么给出区间和依据，要么删掉。

### 9.2 逐条对照清单

| 找这种写法 | 改成 |
|---|---|
| 开场套话：“随着集成电路技术的发展”“在当今……的背景下”“值得注意的是”“下面从三个方面介绍” | 删掉，第一句直接给事实 |
| 结尾套话：“综上所述”“总而言之”“通过本次设计，我们深刻认识到” | 删掉。需要收尾只写新信息，比如尚未完成的部分和下一步 |
| 客套与空展望：“希望对大家有所帮助”“未来可期” | 删掉 |
| 对比句式：“不是 A，而是 B”“与其说 A，不如说 B” | 直接说 B |
| 递进句式：“不仅……而且”“不仅……更……” | 拆成两个陈述句 |
| 硬凑三项：三个排比形容词、每组都正好三项的列表 | 有几项写几项 |
| 设问自答：“关键在哪里？答案很简单：”“原因其实很直接：” | 直接给结论 |
| 宣传腔与黑话：强大、灵活、无缝、全面、极致、优雅、一站式、赋能、闭环、打通、抓手、底座、颗粒度 | 换成具体事实，没有事实就删 |
| 破折号插入解释 | 改逗号、冒号、括号，或拆成两句。全篇最多一两处 |
| 翻译腔：“进行 + 动词”“通过……的方式”“作为一个……”“起到了……的作用” | 直接用动词。写“修改配置”，不写“对配置进行修改” |
| 过度含糊：“在某种程度上”“在一定情况下可能会” | 确定就直接说，不确定就写条件与验证方法 |
| 主持腔过场句：“这一节我们来看一下”“接下来进入正题”“先把这件事单独拿出来说” | 删掉，让下一句直接开头 |
| 每段都加粗、一两句话也拆成列表、小标题比正文还密 | 按 §3 重排。加粗只留真正的警告与关键词 |
| 感叹号、emoji、装饰性符号 | 换成句号与纯文字 |

### 9.3 交稿流程

1. 先按 §7 的章节和字数上限搭骨架，每节先写清“这节要回答什么问题”。
2. 从 `docs/` 与 `release/evidence/` 抽事实填进去，事实优先于措辞。
3. 逐条过 §9.2 清单，命中的全部改掉，不做“温和润色”。
4. 过 §9.1 三条硬要求，数字与证据逐一对上。
5. 查 §2.1 中英空格、§5 全角标点、§4 数值的单位与增减。
6. 通读一遍：超过 40 字的句子、超过 7 行的段落、连续三个列表，全部重写。

### 9.4 一条判断标准

删掉一句话，如果事实、论证和结构都不受影响，这句话就是在替作者占位置，直接删。宁可写短，不要写满。
